v1.0.22 (2026-11-05)  Command window shown before every action by default
  Changed : Environment > General > Commands now defaults to Always: the
            command window (exact PowerShell, Copy, Run / Cancel) opens before
            EVERY action that goes through the command engine, launch and
            read-only actions included (RDP, ping, open folder ...). Before, the
            default was Changes, so launch actions ran straight away and the
            code only showed on Shift+click - easy to miss. Changes / Never are
            still there for anyone who finds it too chatty. A saved choice
            (Settings\Commands.json) is kept.
  Note    : Engine-only; projects take it with Update Template.

v1.0.21 (2026-11-05)  Hover help on everything clickable; "show the exact command" engine
  Added   : Base\Services_ToolTips.psm1 - tooltips for every button, check box,
            radio button, link label, menu item (right-click menus too) and
            tab, from ONE catalog: engine entries (developer buttons,
            Environment tab, OK / Cancel / Close / Export CSV ...) plus the
            project's Config\ToolTips.json (project-owned; wins). Keys are the
            control text, optionally with where it is ("Tools > Ping List >
            Ping", "<dialog title> > Copy"); the most specific match wins.
            Started once by _AppLauncher.ps1 (Start-AppToolTips); dialogs, lazy
            tabs and menus swapped at run time are picked up automatically -
            modules call nothing. Set-AppToolTip sets one in code.
  Added   : Developer build: every clickable control without an entry is
            listed, ready to paste, in <data root>\Logs\ToolTips_missing.txt
            and counted in Session.log ([ToolTips]).
  Added   : Base\Services_Commands.psm1 - anything that runs a script builds the
            PowerShell as text with the real values (Format-AppCommandValue)
            and goes through Invoke-AppCommand (confirm + log + run that same
            text) or Confirm-AppCommand (confirm + log). The command window
            (Show-AppCommandDialog) shows title, summary and the code
            (read-only, selectable) with Copy and Run / Cancel; for a change it
            is the confirmation itself and Enter never runs it.
            Register-AppCommand gives a button right-click "Show command... /
            Copy command" (nothing runs) and adds that hint to its tooltip.
            Every confirmed command is logged ([Command] Run : <title>, the code
            as DIAG).
  Added   : Environment > General > Commands (all environments,
            Settings\Commands.json): show the command before running Always /
            Changes (default: actions passed -Kind Change) / Never. Shift+click
            shows it first whatever the setting.
  Changed : _AppLauncher.ps1 starts the tooltips after the tabs are built.
            Tab 1's "Open data root" is the command-engine example; Config\
            ToolTips.json (project-owned) carries Tab 1-4 entries as the example.
  Note    : Engine-only and additive (no contract change): projects on 1.0.17+
            take it with Update Template. Add Config\ToolTips.json to the
            project for its own controls; until then the developer build's
            ToolTips_missing.txt lists them.

            start and every compile (Build-App, Update, Update Template, Build
            Lite, Build Sealed). The Update and Update Template pickers open
            there. Sealed and Lite EXEs never create it.
  Changed : The Update engine reads only source text files from a zip or folder
            (.ps1 .psm1 .cs .json .txt .csv .xml .md .cmd) and skips Update\,
            Archive\ and dot-folders, so EXEs or zips beside a source folder are

v1.0.17 (2026-11-01)  Update Template button; identity in AppIdentity.json; wildcard filters

            grid or tree: * = any text, ? = one character, in any position;

  Added   : Tab 2 is now the reference filterable grid (template only; Tab 2 is

  Changed : Project identity moved from the PROJECT IDENTITY block in AppHost.cs

  Changed : Update keeps the project's identity: an update without

  Changed : The drift check also covers AppHost.cs and Build-App.ps1 (their

  Fixed   : TEMPLATE_FILES.txt in v1.0.16 listed an out-of-date hash for
            AppHost.cs. It went unnoticed because AppHost.cs was not checked.
  Fixed   : AppHost.cs had non-ASCII bullet characters in string literals; they

  Contract: Every project needs AppIdentity.json at its root with its AppName,
            ExeName and AppDataFolder (the values from its old PROJECT IDENTITY
            block - the same AppDataFolder keeps its environments and logs).
            This step is a manual sync (one update zip per project); Update

  Note    : Versioning from here: 1.0.x = engine-only (Update Template applies
            it); a new major.minor = contract change (manual sync).

v1.0.16 (2026-10-25)  Post-update archive: resumable, logged, faster
  Fixed   : The Lite build could be skipped: the archive steps ran as one unit
            after a slow environment scan, and closing the app before they
            finished (they run in the background) silently stopped them. Each
            step (EXE copy, source zip, Lite build) now runs on its own, is

  Changed : The archive's source zip skips the "Get-Module -ListAvailable" scan
            (Environment.txt without the module list); Extract still includes it.
  Added   : Closing the app while the archive / Lite build is running asks first.
            The status bar shows the step (1/3, 2/3, 3/3) and what was not done.

v1.0.4  (2026-10-22)  Run the message loop through PowerShell (fixes try/catch in handlers)
  Fixed   : Event handlers (button clicks etc.) that use try/catch/finally threw
            a NullReferenceException in SuspendStoppingPipeline, because the C#
            host owned the WinForms message loop so no PowerShell pipeline was
            active on the event thread. The loop now runs THROUGH the runspace
            (RunMessageLoop() invokes [Windows.Forms.Application]::Run), keeping a
            pipeline alive for the whole UI - exactly how the source tool hosted
            it. Simple handlers (no try/catch) were unaffected, which is why this
            surfaced only once a handler used error handling.

v1.0.0  (2026-10-21)  Generic project template baseline
  Added   : Single-EXE PowerShell project shell (portable; copy one file).
  Added   : Two build flavours from one source.
            - DEVELOPER build (never distributed): embedded plaintext package
              (all module tiers) + embedded C# source + full tooling. Runs with
              no password and loads every tier.
            - SEALED build (the single distributable): no source, no tooling.
              Two AES-256 bundles embedded - UserBundle (Base+Lite) and
              AdminBundle (Base+Lite+Admin) - each keyed by PBKDF2(password).
              It prompts for a password at launch; the bundle that password
              decrypts decides the tier. No key is stored in the binary, so the
              modules of a tier you cannot unlock stay encrypted at rest.
  Added   : Baked-in look and feel (Segoe UI / Consolas, the blue palette and
            flat buttons from the sample), exposed to modules as $App.Theme and
            applied to the window, tabs, status bar and dialogs.
  Added   : Module tiers - Modules\Base (shared), Modules\Lite (all users),
            Modules\Admin (admin only, empty by default). Admin-tier tabs appear
            only when their module is present (developer build or admin password).
  Added   : In-app Update engine (developer build) - apply an update zip/folder,
            preview add/modify/delete, recompile the developer EXE, archive the
            old one to Archive\.
  Added   : Build Sealed (developer build) - mint the distributable: set a user
            and an admin password, seal the two bundles, compile source-stripped.
  Added   : Extract, Function Map, Environment capture, Version History
            (developer build only).
  Added   : Tabs - Overview (template guide), Tab 1 (wired example), Tab 2-4
            (placeholders), and Defaults. The Defaults tab holds the environment
            dropdown + that environment's fields; picking one makes it active and
            refreshes the fields. Fields are editable in the developer build
            (Save writes Config\Environments.json, read live) and read-only in a
            sealed build - edit in dev, rebuild to ship.
